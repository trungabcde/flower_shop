# Реализация задания №6: пояснения к ТЗ

## Что реализовано

1. **Переиспользование Lab 5.** Основные `products`, `units`, `spec_versions`, `spec_items`, `spec_variants` и конфигуратор не копируются и не переименовываются. Новый модуль импортируется поверх приложения Lab 5.
2. **Модель хранения.** Ровно 19 новых таблиц `routing_*` согласно разделу 4 ТЗ; связи с существующим каталогом/спецификациями, уникальные контексты маршрута, ограничения типов/норм/ставок.
3. **Изделие–Операция.** Узел `routing_nodes` различает покупной ресурс (`purchase`) и производственную операцию (`production`) с именами действия и результата. Нормативные входы задаются `routing_inputs`.
4. **Расчеты PostgreSQL.** Функции `"FIND_TM"` (полный граф), `"MR_Q"` (непосредственные входы), `"SUM_MR"` (конечные закупные ресурсы), `"TR_TO"` (труд), `"ROUTING_COST"` (калькуляция текущих цен) принимают ID маршрута / операции и количество. Общая операция из нескольких ветвей агрегируется до начисления единственного подготовительно-заключительного времени.
5. **API `/api/routing`.** Реализованы все группы URL из раздела 7 ТЗ: адаптеры товаров/версий/вариантов, CRUD новых справочников, цены, маршруты, операции, входы, инструменты, дерево, расчеты, шаблоны и их применения.
6. **Паттерн «Приспособленец».** Общее состояние процесса находится в `routing_typical_processes` + `routing_tp_*`; параметры каждого использования — в `routing_tp_applications` + `routing_tp_values`. Производственные узлы имеют ссылки `application_id` и `template_operation_id`; их нормативы не редактируются как независимые записи.
7. **Контроль ошибок.** Отрицательные нормы/количества, самоссылки, циклы графа, смена используемых маршрутов/шаблонов, недопустимые параметры и отсутствие учетных цен приводят к ошибкам вместо молчаливого исправления.
8. **Демонстрация API.** `demo_lab6.py` создает контрольный букет, вложенный подарочный набор, два применения шаблона `size=1/2` и несколько дополнительных примеров (смешанный букет, корзина с губкой, сухоцветы, растение в подарочном оформлении, сложная композиция).

## Разумные уточнения проектирования

- Все 19 таблиц и их основные столбцы сохранены в соответствии с ТЗ; дополнительные индексы запрещают дубли источников типовых операций.
- Для получения ID пользователь использует GET-адаптеры, а не условные числа из примеров 101/201/301/401.
- Свойства `operation_name` и `state_name` БД представляются на API как `name` и `result_name`. Для контекста версии используется `spec_version_id`, для готового результата — `final_operation_id` (в БД `final_node_id`).
- Начальные справочники и товары загружаются отдельным повторно запускаемым скриптом через HTTP, а не закодированы в миграции. Данные Lab 5 не уничтожаются.
- Для ошибок API добавлен единый объект `error {code, message, ...}`; SQL-функции возвращают расчет или поднимают исключение при отсутствии/неполноте данных.
- Для вычисления соответствия BOM используется существующий алгоритм `/bom/expand` или сохраненный снимок варианта; *второй алгоритм конфигуратора* не разрабатывается.
- Модель прав **концептуальная**: флорист — просмотр/изготовление; старший флорист — разработка маршрутов, норм и калькуляция; администратор — ведение справочников и целостности. Новая авторизация и назначение конкретных работников исключены согласно ТЗ.
- Предлагаемые имена файлов (`main_new_lab6.py`, `routing_lab6.py`) выбраны для изоляции от работающего Lab 5; это не отдельная СУБД или новый каталог товаров.

## Ограничения результата и критерии приемки

- Код прошел проверку синтаксиса Python, инспекцию Swagger/OpenAPI вместе с Lab 5, офлайн-тесты формул и API CRUD/типового процесса на временной SQLite. **Полная интеграционная проверка PostgreSQL в базе пользователя еще не выполнена.**
- Только после исполнения `lab6_migration.sql`, `lab6_functions.sql`, `demo_lab6.py` на восстановленной копии PostgreSQL и проверки чисел в Swagger можно считать интеграционную часть принятой.
- Скриншоты DBeaver, реальные ID/ответы Swagger и отчет по формату кафедры создаются на рабочей установке; не подменяются предполагаемыми результатами.
- В системе нет производственных заказов, фактических нормативов/списаний, складского движения, работников и графиков смен, курьерской логистики, стоимости доставки, авторизации, отдельного HTML-интерфейса — это исключено из объема ТЗ.
